# Script area backend

Existing `/api/project-assets/projects/:id/script` reads/writes the same draft, including the original revision conflict behavior. New API prefix is `/api/project-scripts/projects/:projectId`; it uses the existing local session, write token and current `X-Shiguang-Library-Id`. Only material GET/HEAD content also accepts `libraryId` in the same-origin relative download URL. Neither credentials nor local filesystem paths appear in these DTOs.

## Drafts and frozen sources

Read `/draft` for `revision` and the server-generated SHA-256 of UTF-8 `JSON.stringify([title,content])`. POST `/versions` or `/draft/snapshots` with `expected_revision`, `contentDigest`, and UUID `requestId`. A version is an explicit user confirmation; snapshots are agent-accessible draft freezes. The first confirmed version is V1. Existing nonempty drafts become an unnumbered legacy baseline on upgrade, retaining their original timestamp. No historical files are imported as snapshots.

Repeated project/operation/request IDs return the original receipt after a later draft edit; changed parameters conflict. A project row and the existing series-directory lock serialize confirmation, numbering and scope changes. Frozen text never changes when the draft is saved. Sources are read from `/sources/:sourceId` with server line numbering (BOM removed, CR/CRLF normalized, blank lines retained, one terminal newline not an extra line).

## Materials and maps

Current upload parsing and original-byte reads are bounded in-memory operations, not streaming-to-staging; the 25 MiB cap is not a streaming claim. POST `/materials` accepts one multipart `file`, `ownerType` (project or series) and `requestId`, with a 25 MiB file limit. TXT must be UTF-8; PDF/DOCX extension and file signatures are checked. PDF/DOCX originals are not automatically promoted to line-numbered text; users upload a checked TXT counterpart. Same names create separate IDs. Move/delete requests require `expected_revision` and `requestId`. Access is limited to the current episode/project and its own series-wide material. Tombstones hide original downloads and new source reads; existing map excerpts remain available and display the deleted-source state. Only managed copies are considered for cleanup; uncertain bytes remain private.

POST `/maps/dry-run` validates the same `{binding,graph}` as POST `/maps`, returns `{renderData,issues}` with `no-store`, and writes no preview or receipt. Single binding has `target`; diff binding has distinct `before` and `target`, each a project-owned version, legacy baseline or snapshot. Shared browser/server structural validation is `shared/script-map-validation.mjs` (`validateScriptMap(unknown) -> {issues}`); its TypeScript declaration is included. Server checks source ownership before searching, then inclusive line bounds and short quote against one selected line. Quotes have 4–20 Unicode characters after whitespace removal, or equal a complete shorter line. Mismatch may return up to five line numbers from that same authorized source, without text or auto-repair.

Input graph limit: 512 KiB; rendered graph and excerpts: 1 MiB; loaded source texts per validation: 32 MiB. Per-container bounds and early excerpt limits prevent unbounded expansion. Saved/read maps contain normalized graph references without any quote and only server-derived excerpts, never complete sources. Lists paginate after scope/state filtering. POST maps returns 201, identical replay 200; `/maps/requests/:requestId` recovers the original map. Snapshot targets report stale status when the draft advances.

## Upgrade, backup and recovery

New additive tables are registered with the existing SQLite-to-MySQL converter. Existing `project_scripts` is unchanged. Before first DDL with old drafts, a new private, synced draft snapshot is written under the library's `script-upgrade-backups`; the marker and legacy sources are committed together. Repeat startup resumes missing additive tables and never creates a second baseline. Actual-library upgrades or migration require separate user authorization; development uses private synthetic libraries.

The existing creative/storyboard combined backup now includes optional `script_area` tables plus a byte-size/SHA-256/base64 manifest of every active original. It is a complete logical backup; an SQL-only export is insufficient for material files. Validation checks schema, IDs, project/series membership, immutable source relationships, original bytes and map excerpt references before restore. Originals are privately published and synced before a transaction exposes restored metadata; interruptions may leave hidden managed files, never a half-visible record. Re-entry verifies existing bytes and rows instead of overwriting conflicts. Restore keeps a pre-restore backup. Old backups omit `script_area`, retain existing new-area records, and restored old drafts receive an unnumbered baseline where none exists. The restore HTTP body is bounded to 128 MiB; larger logical backups must be split by a future export facility, not reported as a successful partial restore. Unknown cleanup results are retained.

The same checks run on Windows without relying on POSIX mode bits or directory fsync. File sync, identity/hash readback and exclusive publication are required. This does not claim power-loss durability or Windows ACL isolation. Project deletion removes owned version/map/request rows and hides owned materials; a series containing active materials cannot be removed. Original user files are never swept.

## Agent convention A and verification

Agent guides and concierge capabilities allow draft save/read, snapshots, source reads, map preview/upload and reading user-uploaded material lists. They omit finalization, material upload/move/delete actions. Agents must ask the user to finalize in the page and upload missing client material. This is a product convention against accidental actions, not a defense against clients holding the same local HTTP permissions.

Run `node --test tests/script-area.test.mjs tests/script-area-http.test.mjs tests/project-agent-guide.test.mjs` for isolated SQLite/HTTP checks. Native MySQL is explicit opt-in: `SCRIPT_AREA_MYSQLD=/absolute/path/to/mysqld node tests/script-area-native-mysql.mjs`; it initializes its own directory, chooses a random loopback port, rejects 3306/4317 and system sockets, verifies daemon identity, performs actual conversion/restart, and normally closes workers/daemon. It never reads system database credentials. Windows/Ubuntu CI runs the explicit tests and build. Author checks, independent acceptance, merge and deployment are separate milestones.
