# 分镜数据库关联：简化实施规范

日期：2026-11-04。状态：按本方案实施；具体入口与验收见 STORYBOARD.md 和本批次 DELIVERY.md。

本文件依据用户最新约定，取代同目录《规范与数据库设计.md》中关于多份活动分镜、重导入合并、永久历史、采用快照、场景状态和镜头选图的旧设计。旧Schema及示例保留作讨论依据，不再直接作为本期开发输入，需按本文件简化后再实施。

## 1. 用户明确的流程

1. 分镜必须绑定普通项目。没有项目就没有分镜；公共人物库不承载分镜。
2. JSON导入表示“初始化项目分镜”，只接受完整分镜，不接受独立片段。
3. 再次初始化完整覆盖当前项目的分镜正文、场次、镜头、对白、导入编号映射和清单关联，不合并旧内容，不维护分镜历史版本。
4. 完整JSON初始化时，资产匹配以当前项目、同资产类型的规范化唯一名称为依据，只复用未归档档案。初始化完成后用数据库ID关联，姓名从对应原档动态读取；资产改名不要求用户修改分镜副本。
5. 初始化成功后，日常编辑、读取、保存只与数据库交互，不监听或回写源JSON。
6. 当前分镜关联的人物禁止删除。只有新完整JSON初始化成功、该人物不再出现在新清单中且无其他有效关系时，才解除保护。
7. 人物资料允许编辑，永久ID不因改名而变化；受保护不等于所有资料只读。程序不能通过修改人物所属项目/类型或改写ID绕过关系。
8. 人物缺造型或参考图不阻止初始化和关联。本期不要求选择造型、状态或图片，也不新增相关必填校验。
9. 不增加分镜历史版本表、采用快照表、三方合并、片段覆盖、版本恢复或跨文档同步流程。
10. 用户确认：重新初始化不保留改名前身份的对应关系。A中的陈川改名陈海后，B若仍要求陈川且当前项目没有未归档陈川，则新建陈川并关联；B未要求陈海时，成功初始化后解除陈海的分镜关系，档案与图片保留。旧JSON编号、旧来源映射或任何输入数据库ID均不能绕过本次名称匹配规则。

## 2. 建议采用的简化边界

以下是为避免歧义确定的本期实施默认：

- 一个普通项目只有一份当前活动分镜，数据库对project_id唯一。再次初始化就替换这一份，避免出现“覆盖所有分镜究竟是哪一份”的问题。
- “初始化项目分镜”不重建项目身份，不重置项目资产原档、已有造型/图片、音乐音效使用记录、时间线或提示词模板。成功后留下的新清单之外的资产不自动删除，只有关联解除。
- 场景、道具与人物采用相同的名称匹配、清单关联和删除保护规则，避免正文仍指向已经被移除的档案。
- 用户最新约定：归档字段未归档为0，归档为UTC毫秒时间戳。落实到三类共表的唯一键为`(project_id,kind,name_key,archived_at)`，人物/场景/道具各自限制；name_key继续按NFC规范化、去掉首尾空白、英文字母转小写计算，不做包含/相似/别称匹配。未归档同名的新增或改名返回“该名称已存在”，不同归档时间的同名记录可以并存。
- 已归档人物不自动恢复或用于新分镜关联。名称匹配仅查未归档档案；只有已归档同名时，按该联合约束可以建立新的未归档人物，两者数据库ID不同。
- 保留现有资产删除语义：解除保护后允许使用既有删除/归档入口，默认仍是软归档，不自动抹除图片或原文件。若未来要永久删除资产，需另定清理子项及来源记录的范围。
- 仍可在首次初始化确认中选择/创建目标项目；重复初始化使用已选项目ID，不根据新JSON项目名称切换项目或重命名原项目。

## 3. 关联按清单判断

删除保护依据项目当前分镜的完整素材清单，与镜头对白数量、镜头是否显式引用、是否填写造型图片无关。

例：JSON A的清单有陈川，初始化后复用/创建人物ID X，并建立分镜→X关系。陈川即使没有对白、所有镜头都未填写人物字段，也不允许删除。

导入JSON B时，只有数据库事务成功将当前分镜及完整清单切换为B、且B不包含陈川，X的该条关联才解除。X的资料和图片继续保留，用户此后可按删除规则移除。若B初始化失败，A的分镜和X的关联都保持。

日常删除镜头、删除对白、清空动作文字不解除清单保护。界面不提供绕过初始化直接删除清单人物的操作。若未来允许编辑清单，需要单独改变此规则，不能悄悄通过编辑正文清空关系。

新加入的镜头人物/场景/道具若确实需要使用，选择已有项目资产或创建资产时自动加入当前清单与关联；解除保护仍走完整重新初始化。自动保存对清单删除、替换资产映射进行服务端限制，不能只禁用前端按钮。

## 4. 本期数据库设计

继续使用当前SQLite或当前MySQL单库；没有双写或第二套数据库。

### 4.1 复用

`media_projects`保存项目；`creative_assets`保存人物/场景/道具，`creative_looks`和`creative_image_bindings`保持现状；真实媒体仍在`assets`及原文件系统中管理。

本期不新增场景状态表，不修改造型或图片的业务结构。根据用户最新约定，拟把现有`UNIQUE(project_id,kind,name_key)`改为`UNIQUE(project_id,kind,name_key,archived_at)`；creative_assets.archived_at改为非空整数，默认0。迁移将现有活动资产的NULL回填为0，保留既有归档时间；不再新增is_archived布尔字段。更新资产主档的状态判断、名称检查、读写、前端筛选和备份恢复适配，不能仅修改索引；人物造型/图片子项的旧归档字段暂保持原契约，不混用主档和子项的NULL/0语义。此项属于新的资产schema迁移，需同时覆盖SQLite/MySQL，启动时按版本升级；验收使用隔离库。

### 4.2 storyboard_documents：一份当前分镜

| 字段 | 类型/作用 |
|---|---|
| id | UUID主键，首次初始化创建，再次初始化保留 |
| project_id | UUID，非空且唯一，只能属于普通项目 |
| title | 分镜标题 |
| document_json | 完整当前正文、场次、镜头、对白、规则及清单；资产引用保存数据库ID |
| revision | 正整数并发修订计数，每次保存/初始化递增，不倒退或重置为1 |
| initialized_at | 最近一次成功初始化的UTC毫秒时间 |
| source_filename / source_hash | 最近一次源文件名及内容摘要，仅追溯，不作名称匹配权限 |
| created_at / updated_at | UTC毫秒 |

document_json是数据库字段，非磁盘JSON文件。用户的动作、对白、摄影、衔接及未知字段完整保留。首次解析源JSON的局部人物/场景/道具编号，建立本次源编号→数据库ID转换，完成后不需要外部文件维持编号。

已有镜头/对白ID在日常编辑和排序时稳定，新增/复制由程序分配。重新初始化视为全新分镜内容，可重新生成镜头/对白的内部ID，不要求与旧JSON逐项对齐。

### 4.3 storyboard_asset_links：当前清单资产关联

| 字段 | 类型/作用 |
|---|---|
| id | UUID主键 |
| document_id | 当前分镜数据库ID |
| asset_id | creative_assets.id，不为空 |
| created_at / updated_at | UTC毫秒 |

唯一键`(document_id,asset_id)`，反查索引`(asset_id,document_id)`。类型从creative_assets.kind读取，项目从document/asset归属校验，不再重复存一套名称作为关联依据。

这张表负责删除保护。关系必须覆盖清单全部条目，不能仅从镜头对白推导。正文清单和该表在同一事务内更新，不能通过日常保存擅自移除原关系。显示名称和资料读取当前项目资产原档，正文中的源名称/资料只作来源保存，不能形成另一套可冲突的原档。

逐镜显式关系保存在document_json中的数据库资产ID字段即可。本期不另外增加镜头选图表、采用快照表或复杂镜头使用索引；尚未显式声明逐镜人物/道具的旧JSON不凭长文本自动猜测。

### 4.4 storyboard_import_requests：初始化回执

字段：`id UUID PK, project_id UUID, document_id UUID, request_hash CHAR(64), source_hash CHAR(64), expected_revision BIGINT nullable, result_json LONGTEXT, created_at BIGINT, updated_at BIGINT`。

回执与初始化业务在同一次事务写入；同请求编号+相同摘要返回原结果，不再次覆盖，同请求编号+不同摘要拒绝。查询暂时未找到回执不等于确定失败，必须确认事务/请求已结束后才恢复操作；不能超时后自动使用新请求编号重新初始化。

用户另一次明确确认初始化时产生新请求编号，即使JSON文件摘要与上次相同，也重新初始化并覆盖当前网页编辑；不能套用旧设计的“源文件没变就跳过”规则。只有同一次请求的网络重试才返回原回执。

普通自动保存用expected_revision和当前正文摘要处理无变化与冲突，无需再为每次按键保留完整请求正文、原始文件或历史版本。只保留当前初始化结果的必要技术回执不等于维护历史分镜内容。

### 4.5 技术要求

新增结构仍需要一个模块schema版本标记；UUID为MySQL VARCHAR(36)/SQLite TEXT，时间与修订为BIGINT/INTEGER，正文为LONGTEXT/TEXT，哈希为ASCII二进制比较的固定长度字段。所有新增表均带created_at、updated_at。

不再创建旧设计中的storyboard_bindings、storyboard_asset_snapshots、storyboard_usages、storyboard_media_usages、storyboard_revisions、creative_scene_states等本期无用结构。新增关系逻辑应接入当前SQLite/MySQL的迁移、备份与恢复，不仅创建SQLite表。

## 5. 初始化事务

1. 事务外解析完整JSON，检查结构、清单重复名称、文件内部引用、镜头数量和时间轴。明确标记片段的输入直接拒绝。程序能校验数据一致性，不能凭技术校验证明剧情已完整结束，故确认前展示场数、镜数、时长和清单数量。
2. 生成预览：当前项目、旧分镜将被覆盖、新增/复用资产及解除关联的数量；明确同名归档档案保持归档。确认按钮明确“初始化并覆盖当前分镜”，不称为普通追加导入。
3. 带固定request_id与当前expected_revision提交。所有分镜保存、初始化、删除/归档资产共享项目级锁和同一锁顺序；MySQL事务和SQLite immediate事务内再次核验旧revision与名称。
4. 按名称复用当前项目未归档资产ID。已有档案的描述、造型、图片默认保留，不以新JSON覆盖；只对不存在的活动档案写入初始文字资料。仅有归档同名记录时保持其原状态，按联合唯一规则创建新活动记录，不恢复或挂接归档ID。
5. 写新正文，整体替换当前清单关系，更新revision与initialized_at，写准确回执；全部成功才提交。旧正文/旧关联不能在事务前提前删除。
6. 成功后清空本页面旧草稿、旧撤销栈、旧镜头选择与提示词草稿，载入新数据库数据。其他打开页面的旧revision保存返回409，不能自动换新revision重发旧内容。

不保存上一套正文作为可恢复历史。不因不保存历史就放弃事务内回滚。重置失败保留旧内容；重置成功后不提供“撤回初始化”。

## 6. 不维护历史后的行为

- 分镜与资产关联按当前数据生效。编辑人物原档后，当前分镜中显示和下次生成使用更新后的资料；不再保存每镜采用旧资料的永久快照，也不承诺旧状态可复现。
- 仍保留当前revision用于防止两个页面相互覆盖；一个整数修订不是历史版本库。
- 单次页面编辑的撤销/重做可使用内存操作栈；初始化成功清空，不建立数据库历史表。刷新后的撤销恢复不在本期范围。
- 已有提示词模板/Codex等独立模块的历史功能不因本期精简自动删除；已有资产库的历史表和用户历史数据也不执行清理。本期停止新增分镜历史/快照设计；若用户以后要求取消既有资产模块历史写入，需单独调整其保存与备份恢复契约，不能直接删表。

## 7. 仍需明确展示的实际边界

| 情况 | 处理 |
|---|---|
| 数据库陈川改名为陈海，新JSON仍写陈川 | 这是用户明确要求的初始化行为：当前没有活动陈川则新建陈川；B不含陈海时解除陈海关系。不得以旧编号、别称或来源追踪将两者暗中合并 |
| 已有陈川35岁，新JSON描述40岁 | 复用人物并保留原档，展示资料差异但不覆盖；用户另在资产库修改 |
| 新JSON不含陈川 | 初始化成功后解除关系，陈川留在资产库，由用户决定是否删除 |
| 新JSON清单遗漏但镜头编号引用陈川 | 输入不自洽，初始化前报具体引用错误，不提交半套数据 |
| 陈川出现在清单但没有镜头/对白 | 保持关联并保护删除；不要求补充造型或图片 |
| 同项目清单重复同类名称 | 校验拒绝并指出重复，不建立两套人物或任意合并两份资料 |
| 同名仅存在其他项目/公共库 | 不是当前项目已有；新建当前项目档案或另经既有明确复制流程，不跨项目挂接 |
| 初始化时另一个页面正在保存/删除 | 项目事务锁+revision校验，确定先后结果；禁止旧保存覆盖新初始化 |
| 被引用资产经其他入口归档/删除 | 后端统一校验引用并拒绝，不能只禁用分镜页面按钮 |

## 8. 最新规则的剩余语义问题

### 8.1 编号关联与姓名显示

日常编辑：分镜关联人物ID X，人物X由陈川改名陈海，分镜的人物选择、清单、对白说话人等结构化显示随数据库原档变为陈海，不会新增人物。动作/对白正文等自由文字不自动全局替换名字，避免改写台词或误替换同字词；正文修改仍由用户明确编辑。

再次完整初始化：所有资产关系重新按当前项目的活动名称解析，不追踪改名身份。新JSON要求陈川，而当前只有ID X的陈海时，新建ID Y的陈川，建立新分镜→Y的关系。若新清单不含陈海，则解除旧分镜→X的关系；陈海原档保留。若B同时列陈海，则按名称复用X并继续关联。新JSON中的局部编号只用于解析该文件自己的镜头引用，不与旧文件编号比较，也不作为保留旧关联的凭据。

### 8.2 归档时间唯一键

未归档的archived_at固定为0，同项目同类型同名只能一条；已归档的archived_at为正整数UTC毫秒，不同时间戳允许同名多条。归档操作在项目事务锁内为相同名称分配不重复的归档时间，可用max(当前毫秒,该名称已用归档时间最大值+1)，避免同一毫秒的唯一键碰撞；不能靠睡眠或吞掉约束异常解决。

恢复操作明确设置archived_at=0，已有活动同名时返回“该名称已存在”，不覆盖或合并。初始化忽略归档人物，不自动恢复；旧人物解除分镜关联后才可按保护规则归档。

### 8.3 新建重名与初始化复用

“手动新增/改名要使用已占用名称”返回重名，与“初始化查到已存在活动人物就复用”不冲突，初始化复用本身不执行INSERT。一个数据库记录也可能与外部JSON对年龄、描述有不同表述，唯一键只能防止重复记录，不能使两份输入文本自动一致。当前默认复用并保留资产库原档，源JSON差异不创建第二个人物，也不自动覆盖资料。
