# 拾光分镜发布

你就是当前导演对话的执行者。利用本对话已确认的内容整理分镜，通过随附脚本读取和提交到拾光；无需另开对话，也不经过网页内的“自由管家”。未采纳的建议、已废弃版本和不确定细节不能当作最终分镜提交。

## 使用条件与目标

- 需要本机文件/命令执行能力、Node.js 22 或更新版本，以及正在运行的拾光素材管理器。仅有文字的网页对话不会因加载技能获得这些能力；能力缺失时说明尚未提交，可返回 JSON。
- 将 `scripts/publish.mjs` 解析为相对本 SKILL.md 的**绝对路径**，以下用 `PUBLISH_SCRIPT` 指该路径。不得依赖当前导演项目的工作目录，不必查找素材管理器源码。
- 默认服务是 `http://127.0.0.1:4317`。自定义地址仅接受用户明确指定的本机端口；连接失败就报告，不扫描端口、不启动/重启服务。
- 首次须有目标项目的精确名称或 ID。聊天名、文件夹名、当前网页选项只可作为线索，不能自行决定写入目标。有同名或含糊目标时列出候选，让用户选一次。
- 可以在导演项目根目录保存 `.shiguang-storyboard-target.json`，绑定素材库身份和项目 ID；以后沿用此映射。映射只存地址/身份/项目，不存令牌。项目改名不会改变绑定；换库或修改绑定须明确处理，不能悄悄改投其他项目。

## 工作流程

1. **读取当前项目和最新协议。** 不确定名称时执行 `projects`。已明确目标则执行 `read`；它会创建本地私有工作目录，包含当前 `project.json`、完整 `current.json`、两种实时格式规范与示例。记录输出中的项目 ID、是否已初始化和修订号。

   ```bash
   node "$PUBLISH_SCRIPT" projects
   node "$PUBLISH_SCRIPT" read --project '用户指定的精确项目名称' --remember '/导演项目绝对路径/.shiguang-storyboard-target.json'
   # 后续在同一导演项目中：
   node "$PUBLISH_SCRIPT" read --target-file '/导演项目绝对路径/.shiguang-storyboard-target.json'
   ```

2. **整理候选，选择操作。** 先读 [格式与接口细节](references/protocol.md)。
   - **已有分镜的日常更新**：复制刚读取的 `project.json` 为新候选，仅改用户要求的镜头/场次/对白。保留文档、人物、素材、镜头的永久 ID，以及未修改字段和未知扩展。添加新镜头用新的 UUID；保留已有镜头 ID。对发生内容变化的镜头增加其 `revision`。不要用全新生成的整套 JSON 替代局部修改。
   - **空项目首次初始化**：整理符合读取到的 `initialization-schema.json` 的完整 2.0.0 中文 JSON。三类素材清单均须存在，可以为空；编号、引用和累计时长必须自洽。
   - **已有分镜整套覆盖**：仅在用户明确要求“覆盖/重新初始化/替换整套”时使用完整初始化；普通“更新”不自动等同覆盖。它会重建镜头标识，原视频定位或镜头引用可能需要重新关联。已有资产按服务端规则复用，不自行删除媒体文件。
   - 涉及新人物/场景/道具清单而日常更新不支持时，说明所需操作差异，不以偷偷改数据库或自动覆盖解决。

3. **准备提交与检查差异。** `prepare` 不保存分镜，生成固定候选、提交前副本、逐字段差异或初始化预览。查看 `diff.json`、警告、镜头数、总时长与素材复用/新建清单，核实符合本轮用户要求。禁止为了通过校验自动缩短剧情或删对白。

   ```bash
   node "$PUBLISH_SCRIPT" prepare --session '/读取返回的工作目录' --input '/候选JSON绝对路径' --mode update
   # 首次初始化或明确整套替换时，改用 --mode initialize
   ```

4. **按已有授权提交一次。** 用户已经明确要求“提交/同步/更新到某项目”且目标/范围清楚时，完成候选检查后直接推进，不再次索要例行批准。仅讨论、生成候选或校对不授权写入。用户尚未指定目标、或要求与将发生的整套覆盖不一致时，只澄清缺失部分。

   ```bash
   node "$PUBLISH_SCRIPT" commit --plan '/prepare返回的计划目录' --allow-write
   # 已有分镜且用户明确要求整套替换时，另加 --replace-current
   ```

5. **回读后报告结果。** 只有脚本返回 `verified` 才报告“已提交并回读核实”，列项目、修订号、镜头数及本次修改范围。`already_submitted` 是原已核实回执，代表本次没有重发；要确认当前状态执行 `check`。不要把 JSON 生成、预览通过或请求发出当成提交完成。

## 冲突和失败

- 版本/初始化代次/关联资产变化：重新 `read`，将本轮修改合并到最新副本，再准备新计划；不能直接把旧副本强盖回去。
- 超时、断连、提交后回读不一致：保留原计划，用 `check --plan ...` 查询原初始化请求或核对当前内容；不自动重发、不换请求 ID 重试。普通更新没有独立耐久请求回执；响应丢失但内容匹配只能报告“当前内容匹配，原提交归属未核实”。
- 校验错误显示具体字段路径，修正候选，不删门、不靠接口容错重新解释镜号/时间。
- 不读真实数据库文件/凭据，不修改应用代码、服务配置、素材文件或安装依赖；不启动模型任务，不提交/推送 Git。用户只要求更新分镜时不顺便修改人物资料、剧本或视频关联。
- 工作目录内保留本次候选、提交前副本和回执供核对；不要把整个导演对话或敏感认证信息写入共享技能。
